# avocado_tegraflash

This is a stdlib-only Python port of the Jetson stone provisioning script, started by a thin shim. The differential harness under `tests/parity` proves it equivalent to the frozen legacy script, case by case, for every profile entry.

Run it as `python -m avocado_tegraflash`. Pass `--prepare-only` to stop after the work directory is prepared, before anything is flashed.

The flash needs root. Without it the engine refuses before any USB action with:

```text
Run the same command again with sudo, keeping the environment and PATH:
  sudo -E env PATH="$PATH" <the command you just ran>
```

## Deviations from the legacy script

- `root-check-first`: the engine checks for root before any USB action; the frozen legacy script has no root check at all (only its scarthgap copy checks, and checks first).
- `absolute-cpp-wrapper`: the engine's cpp wrapper execs an absolute path, where the legacy script's execs a bare `cpp`.
- `unknown-profile-refused`: the engine refuses an unknown profile name and lists the five accepted names, where the legacy script takes its default branch and flashes NVMe.
- `one-board-only`: the engine refuses to flash unless exactly one board is in recovery mode, at the wait and again just before the flash, where the legacy script went ahead with whichever board the flash tool picked.
- `carrier-values-literal`: the engine writes carrier values literally, where the legacy script's sed substitution corrupts values containing `&` or backslash sequences.
- `boardctl-single-arguments`: the engine passes the boardctl target and serial as exactly one argument each, where the legacy script's unquoted expansion splits a value with whitespace.
- `prepare-only`: the engine can stop after preparing the work directory, where the legacy script always flashes.
- `symlink-destination-replaced`: the engine replaces a symlink at a copy destination, and copies a staged `boot.img` link before the boot image helper rewrites it, where the legacy script's plain `cp` and the helper write through the link (and `cp` fails on a dangling one, or creates its target as root).
- `env-key-missing-refused`: the engine refuses when `BOOTDEV`, `ROOTFS_DEVICE` or `EXTERNAL_ROOTFS_DRIVE` has no line in `.env.initrd-flash`, where the legacy script's `sed` changes nothing and the board flashes with the wrong boot device.
- `carrier-label-optional`: the engine proceeds when `carrier.env` has no `CARRIER_LABEL` line, where the legacy script aborts (its `grep` fails under `set -e` and `pipefail`, line 191).
- `mkbootimg-missing-refused`: the engine refuses, naming the tool and the tools directory, when `avocado-tegra-bootimg` or `mkbootimg` is missing or not executable there, where the legacy script starts the boot image helper with an empty argument; a failing helper is likewise named by the engine and exits silently in the legacy script.
- `tos-name-bare-filename`: the engine refuses a `TOSIMGFILENAME` that is empty, is not a bare file name of letters, digits, `.`, `_`, `+` and `-` (`.` and `..` included), is set in any form but a plain column-0 assignment, or equals the name another image is staged under (the rootfs, var, initramfs, `esp.img`, `initrd-flash.img`, `kernel_<dtb>` and the rest), naming the file and the value and before any image is copied, where the legacy script uses the value as a path, so `..` escapes the work directory and a collision replaces an image.
- `layout-placeholder-unique`: the engine refuses a layout where `APPUUID` or `APPUUID_b` occurs other than exactly once, where the legacy script's `sed` fills every occurrence and two partitions get the same GUID.
- `carrier-value-shell-safe`: the engine refuses a carrier key that is not a shell identifier and a carrier value containing a double quote, dollar sign, backtick, backslash or newline, naming the key and the file, where the legacy script writes them into files that bash sources as root.
- `build-dir-locked`: the engine refuses to run while another provisioning run holds `<build dir>/tegraflash.lock`, where the legacy script has no lock and two runs restage one tree under each other.
- `env-file-missing-status`: a BSP without `.env.initrd-flash` makes the engine exit 1 with an error naming the file, where the legacy script exits 2.
- `recovery-pids-widened`: the engine counts the product ids 7819, 7919, 7026, 7226 and 7326 (the Thor and newer ids from the upstream finder and L4T) as recovery devices, so a board with one of them and no APX or RCM text is found, where the legacy script's `check_rcm` lists only ten ids.
- `cmdline-control-chars-refused`: the engine refuses a control character or newline in `AVOCADO_KERNEL_CMDLINE` or `AVOCADO_KERNEL_CMDLINE_EXTRA`, naming the variable, where the legacy script passes them to the root-run boot image helper.
- `required-image-refused`: the engine refuses, naming each key or file, when a manifest image it must flash (rootfs, var, initramfs, tegraflash_initramfs, tegraflash_esp, tegraflash_tos) has an absent key (tegraflash_tos included, so all six are mandatory), a source that is absent, not a regular file or empty (one refusal lists every absent key and every unusable file), a value whose last path component is empty, `.` or `..`, or two images that would be staged under one name (including the fixed `esp.img` and `initrd-flash.img` destinations, so a rootfs and an ESP image both named `esp.img` are refused naming both keys), where the legacy script warns and flashes anyway, or lets the later copy replace the earlier.
- `partition-fit-refused`: the engine refuses, naming the image and the partition, when the rootfs or ESP image is larger than its partition in the layout the flash applies, where the legacy script flashes it anyway. The check reads the staged `external-flash.xml.in`; the flash later rewrites the `<filename>` of same-named partitions from the signed layouts (`external-secureflash.xml`, `internal-secureflash.xml`), which the engine does not read, so the check covers what the staged layout says and not what those copies say. The flash's `sed` also runs over the whole text of its layout copy, while the engine scans only `<filename>` text (every `<filename>` child of a partition, so a partition that repeats the element has each one checked), so a placeholder or rename match written anywhere else in the XML (a `<name>`, an attribute, a comment) is rewritten without the engine seeing it. It also covers the staged `ROOTFS_IMAGE` (the last plain assignment in `.env.initrd-flash` or `.presigning-vars`, which a carrier overlay can rewrite; any value other than the staged rootfs name is refused), the APP and APP_b layout `<filename>` entries (each must be the `APPFILE` or `APPFILE_b` placeholder, or the staged rootfs name) and the esp `<filename>` (it must be present and equal `esp.img`), and measures against the smaller of APP and APP_b; an absent APP_b leaves APP as the limit. More refusals follow the flash's own `sed` over a copy of the layout, which reads every `<partition>` element whether or not it has a name or repeats one: any partition other than APP and APP_b whose `<filename>` contains `APPFILE` (the flash would write the rootfs into it), any partition other than `DATAPART_EXPAND` whose `<filename>` contains `DATAFILE`, any partition other than the kernel-dtb ones (`A_kernel-dtb`, `B_kernel-dtb`) whose `<filename>` contains `DTB_FILE` (`BPFDTB_FILE` counts: `initrd-flash.sh` rewrites this layout with `s,DTB_FILE,...,` and no leading space, unlike the flash helper's `s, DTB_FILE,`, which reads a different file), and any layout filename or staged image (the TOS destination from the env file included) that matches `<rootfs name without its last extension>.img` (the flash rewrites a match into the rootfs name; the pattern is read as a GNU sed basic regex, so it is unanchored, its `.` matches any character and every other character is literal). A layout filename that is exactly the rootfs name is accepted in APP and APP_b only; in any other partition the flash would write the rootfs there with no fit check, so it is refused. A partition size is read only as plain decimal or `0x` hex (`1_0`, `+5`, `0b11` and `010` are not numbers and refuse). A layout containing `oem_sign="true"` is refused too, because the flash then rebuilds the filenames from a signed copy. `--prepare-only` runs this check too, with no board: it skips the recovery wait but not the fit. The check runs after the recovery wait for every profile, in the oracle's call order, so an oversize image is refused only once a board is in recovery mode; the `avocado-flash nvme` wrapper runs its own fit check before it pins a board.
- `recovery-id-pinned`: the engine refuses a recovery device whose USB id is not in the manifest's `rcm_ids`, naming both ids, where the legacy script flashes whichever board it finds.
- `env-append-newline`: when the NVMe pin has to be appended to a `.env.initrd-flash` whose last line has no newline, the engine starts a new line for `ROOTFS_NVME_PCI`, where the legacy script's `echo >>` glues it onto that line.
- `device-confirmation`: the engine asks the operator to retype the recovery device before an erasing flash, per the `AVOCADO_PROVISION_FORCE` decision table (`1` skips; `0` retypes on a terminal and refuses without one; unset or empty retypes on a terminal and proceeds with a logged note without one; any other value is refused), where the legacy script flashes without asking. The prompt names the device node next to the medium (`nvme (nvme0n1)`), and names `emmc` whenever the flash would erase it: a flag added it, or the staged env has `EXTERNAL_ROOTFS_DRIVE=1` and no `NO_INTERNAL_STORAGE=1`, which makes `initrd-flash.sh` emit `erase-mmc`. The engine reads `ROOTFS_DEVICE` and `EXTERNAL_ROOTFS_DRIVE` back from the staged env files and refuses when either differs from what the profile wrote.
- `path-filter`: the engine keeps only absolute `PATH` components, once, before any tool lookup, logs the dropped ones by name, and falls back to the system path when none is absolute, where the legacy script resolves tools through the `PATH` as given, so a relative or empty component can stand in for a tool that runs as root.
- `unpinned-kernel-refused`: the engine refuses, naming `AVOCADO_PROVISION_KERNEL_IMAGE` and `AVOCADO_PROVISION_ALLOW_UNPINNED_KERNEL`, when no kernel image is pinned and the opt-out is not exactly `1`, before staging or board contact, where the legacy script flashes the prebuilt `boot.img`.
- `unidentified-board-refused`: the engine refuses, naming `AVOCADO_PROVISION_RCM_ID`, before waiting for a board when the manifest declares no recovery ids and `AVOCADO_PROVISION_RCM_ID` is not set to one (on a terminal the operator retypes the device, with a note that the board is not identity-checked), where the legacy script flashes whichever board it finds.
- `rcm-id-override`: `AVOCADO_PROVISION_RCM_ID`, a lowercase `vid:pid` of four hex digits each, replaces the manifest's recovery id list at the wait and the recheck, and a malformed value is refused before anything is staged, where the legacy script has no such override.
- `dry-run-env-prepare-only`: `AVOCADO_PROVISION_DRY_RUN=1` behaves as `--prepare-only` (no root check, no board contact, no prompt) and any other non-empty value is refused naming the variable and value, where the legacy script has no dry run.
- `fwup-task-refused`: the engine refuses, naming `AVOCADO_PROVISION_FWUP_TASK` and its value, when it is set to anything but `complete`, before staging, where the legacy script has no firmware update task and always flashes a full image.
- `boot-tools-from-tools-dir`: the engine starts `avocado-tegra-bootimg` and `mkbootimg` by absolute path from the tools directory the manifest names and never consults `PATH`, so a same-named program earlier on `PATH` cannot stand in for a helper that runs as root, where the legacy script looks them up through `PATH`.
- `force-policy-table`: `AVOCADO_PROVISION_FORCE` follows one decision table shared with the shell library's `confirm-vectors.tsv`: `1` skips the prompt, `0` retypes on a terminal and refuses without one, unset or empty retypes on a terminal and proceeds with a logged note without one, and any other value is refused naming the variable and value, where the legacy script has no confirmation.

## Staged env file

`initrd-flash.sh` sources `.env.initrd-flash`, and then `.presigning-vars` when the work directory has one, with bash, so the last assignment of a variable in any shell form wins. The engine never runs either file.

The BSP and carrier files are as trusted as the flash tools that source them as root, so the engine guards against mistakes and generated-file drift, not against a hostile overlay (a hostile carrier can already replace `./initrd-flash`). It lints with an allowlist:

- The checked keys are `ROOTFS_IMAGE`, `ROOTFS_DEVICE`, `DATAFILE`, `EXTERNAL_ROOTFS_DRIVE`, `NO_INTERNAL_STORAGE` and `TOSIMGFILENAME`. Pure comment lines are skipped.
- A checked key may appear as a bare word in exactly two forms: a plain column-0 assignment `KEY=value`, and a read written `$KEY` or `${KEY}`. Any other line mentioning one (`export`, `declare`, `eval`, `printf -v`, `read`, `unset`, an array element, `+=`, a space before `=`, indentation, a `;`, `&&` or `||` chain, `${KEY:=...}`) is refused, naming the file, the line and the key.
- A line with `eval`, `source` or `.` as a command word is refused because the engine cannot follow it. The command word is looked for as the first word and after `;`, `&&`, `||`, `|`, `&`, `{`, `}`, `(`, `)` or a backtick; before it the reader skips the reserved words `then`, `do`, `else`, `elif`, `if`, `while`, `until`, `!` and `time` (with its `-` options), the wrappers `builtin`, `command`, `exec` and `env` (with their `-` options), leading `NAME=value` assignment words, and leading redirections (`>file`, `2>file`, `> file`, `<file`, `2>&1`). Quote marks and backslashes inside the command word are dropped, so `'source'`, `"."` and `\source` are refused. A line ending in a backslash and a file with a NUL byte are refused too. The reader splits a line on whitespace and on the separators above without tracking quotes, so a quoted value that contains one (`X="a; . b"`) is refused, which fails closed, and a quoted-space assignment prefix such as `x="a b" . f` is not recognized as hiding a source. Not recognized (the reader does not parse shell): an assignment or redirection target holding a space inside quotes (`X="a b" . f`), a command word built by expansion (`$cmd f`) and `exec -a name` style options that take an argument.
- A value is unquoted once (one matching pair) and must match its shape: `ROOTFS_IMAGE`, `DATAFILE` and `TOSIMGFILENAME` a non-empty bare file name of letters, digits, `.`, `_`, `+` and `-` (not only dots), `ROOTFS_DEVICE` the same without `+`, `EXTERNAL_ROOTFS_DRIVE` and `NO_INTERNAL_STORAGE` `0` or `1`. An unmatched quote, `$`, a backtick, `;`, `&`, `|`, parentheses, whitespace or a backslash refuses, and so does an empty `DATAFILE`. A trailing `# comment` after a value and a CR from a CRLF line ending are refused by name, not as an unmatched quote. The env files have no size cap; the reader is linear in their length, and a 4 MB file of one million short lines took 1.5 s to read in one measurement.

After the boot device is applied the engine reads the files back and refuses when `ROOTFS_DEVICE` or `EXTERNAL_ROOTFS_DRIVE` differs from what the profile wrote, or `DATAFILE` is not the staged var image name. An absent `DATAFILE` is refused too, because the flash then deletes the data partition entry from its layout. The confirmation prompt names `emmc` when the flash would erase it. The `TOSIMGFILENAME` destination goes through the same reader. Each refusal cites the file and line that set the value, which is `.presigning-vars` when that file's assignment won. The variables the engine checks are removed from the environment the flash runs in, so an exported variable in the caller's shell cannot stand in for a line the files leave out. The check runs once the files are final, after the carrier overlay and the boot device rewrite, and before the fit check.

## Recovery id and flash confirmation

Two inputs control which device the engine writes and whether it asks first.

`storage_devices.rootdisk.tegraflash.rcm_ids` in the stone manifest is a list of lowercase `vendor:product` USB ids. With ids declared, the engine refuses any recovery device not listed and names both ids. Without ids it warns that the board is not identity-checked and proceeds with exactly one recovery device. The list only narrows the match: a device is still recognised as a recovery device by its APX or RCM description or by `RECOVERY_PIDS` in `usb.py`, so an id outside both is never found. The Orin Nano manifest ships only `0955:7523` (seen on the bench); other boards carry none until an id is observed on hardware. The host wrapper's `--rcm-id` is checked by the wrapper only, so the engine still refuses an id the manifest does not list.

`AVOCADO_PROVISION_FORCE` has three states:

- Unset: the engine prompts on a terminal; otherwise it prints that the confirmation was skipped and proceeds.
- `0`: the engine requires a terminal and prompts, and refuses without one.
- `1`: the engine skips the prompt.

Any other value is refused. The prompt asks the operator to type the recovery device's `bus:device`.
